## 三、实测发现、但项目书完全没写的问题

### 1. `description` 是 Python list 字面量字符串（两个数据集都有）

数据集 A 的 JD 正文 **100%** 长这样：

```
['1.\xa0\xa0 以用户增长为导向，对数据进行深度挖掘和分析…；', '2.\xa0\xa0 能够持续动态的挖掘日常的业务数据…']
```

数据集 B 的 `salary` 列同理，是字符串形式元组 `'(25000.0, 50000.0)'`。

**必须用 `ast.literal_eval()` 解析后 `"".join()`**，不能用 `str.strip("[]")` 或正则——正文里含中文逗号、单引号和 `\xa0`（不间断空格）。项目书的清洗章节没有这一步。

### 2. 数据集 A 里只有 29.9% 的行命中技能（全量口径）

| 口径 | 至少命中 1 项技能的行 |
|---|---|
| `cleaned_all.csv`（24,185 条） | 7,243 条 = **29.9%** |
| `cleaned_data_jobs.csv`（2,915 条） | 1,873 条 = **64.3%** |

这是**技能抽取的可用上限**。项目书里的"技能词覆盖 75.2%"是数据集 B 的口径，两个数字不能混用——按 24,185 条建库时，七成岗位抽不出任何技能，冷启动的用户画像-岗位匹配会大面积落空。

数据集 A 全量的技能命中率（Top 10）：统计 18.9%、excel 11.3%、ppt 5.3%、sql 3.9%、python 3.1%、数据挖掘 2.2%、java 1.6%、mysql 1.4%、可视化 1.1%、spss 1.1%。

### 3. 两个数据集都不是"校招"数据，且 B 有 40% 不是 IT 岗

数据集 B 的 `label` 分布：

| label | 条数 | 占比 |
|---|---:|---:|
| 数据分析 | 2,650 | 26.2% |
| 经济金融 | 2,095 | 20.7% |
| 生物统计 | 1,939 | 19.2% |
| 算法岗 | 1,898 | 18.8% |
| 大模型相关 | 1,532 | 15.1% |

**经济金融 + 生物统计 = 4,034 条（39.9%）根本不是软件/数据类岗位**。实测 B 的第 2 行就是"百济神州 (Senior) Scientist, Discovery Biology"的生物实验岗，JD 是英文实验流程。项目书说"JD 混入法务样板文"，实测混入的主要是**生物/金融岗**，性质不同但同样要清洗。

数据集 A 的 `experience` 分布：不限 55.8%、3-5 年 25.2%、5-10 年 12.2%、**应届生仅 1,444 条 6.0%**、10 年以上 0.9%。
数据集 B 没有 `experience` 字段。

这直接冲击"校招信息聚合与智能推荐平台"的定位：**两个源都不含校招标识**，只有 A 的 `experience == "应届生"` 一个 6% 的子集能勉强当校招用。这一点必须在项目书里说清楚，否则答辩时"校招"两个字站不住。

### 4. 两源城市分布严重偏斜

| 城市 | 数据集 A | 数据集 B |
|---|---:|---:|
| 广州 | 16.4% | — |
| 深圳 | 15.6% | — |
| 其他 | 15.2% | 18.2% |
| 上海 | 14.0% | — |
| 北京 | **3.1%** | **32.3%** |

A 的北京只占 3.1%，B 的北京占 32.3%。合并成 34,299 条后，"按城市推荐"这个维度的结果会被 B 主导，且"其他"桶合计约 5,500 条无法落到具体城市。

### 5. 两源几乎没有任何重叠岗位

按 `岗位名|公司` 求交集，两源**只有 3 条重复**。所以：

- 项目书说的"合并 34,299 条"→ 去重后实为 **34,296 条**，几乎不用去重；
- 但反过来说，**两源岗位完全对不上**，不能用 `job_title` 做跨源对齐（实测内连接会炸出 321,544 行的笛卡尔式膨胀）。合并只能取并集，且要做**源标记**（`source` 字段）以便按源分析。

## 四、对项目的直接影响

1. **数据这一环已经真实可用了**，不用再担心"数据集下不到"。项目书里"均已实际下载验证"这句现在是真的了。
2. **要改的地方**：18 个技能列（不是 12）、`publish_date` 是 `MM-DD` 无年份、459→464 条、MIT 授权表述、THUOCL 两列格式——5 处小改。
3. **要补的地方**：`ast.literal_eval` 解析步骤、"全量口径技能命中率仅 29.9%"这个冷启动风险、B 有 40% 非 IT 岗、"两源均无校招标识"。
4. **最该重新考虑的一点**：既然两源都没有校招标识、A 全量技能命中率只有 29.9%，那么"技能标签 → 加权匹配"这条主线的数据基础比项目书假设的弱不少。建议**把 `cleaned_data_jobs.csv`（2,915 条纯数据岗，技能命中率 64.3%）作为主训练/演示集**，`cleaned_all.csv` 只做统计图表的规模底座——这样推荐效果的演示会好看得多，且工作量不增加。
