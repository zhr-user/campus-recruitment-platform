## 1. 项目背景与目标

### 1.1 背景

高校毕业生规模持续增长，校招信息分散在 BOSS直聘、智联招聘、前程无忧、实习僧、牛客网等多个平台。求职者面临三个具体问题：

1. **信息分散** — 需要反复切换多个平台，重复填写筛选条件
2. **筛选成本高** — JD 文本冗长（实测：数据集 A 的 JD 正文均值 456 字、中位 410 字、最长 9,754 字；数据集 B 中位 286 字、最长 5,687 字），关键信息（技能要求、薪资、城市）埋在其中
3. **匹配靠感觉** — 缺乏量化的"岗位-个人能力"匹配评估，投递决策依赖主观判断

> ⚠️ **数据口径前置说明（实测）**：本项目用作演示的两个离线数据集**都不是校招专项数据集**。数据集 A（24,185 条）中 `experience == "应届生"` 的仅 **1,444 条（6.0%）**，其余为不限/社招经验要求；数据集 B（10,114 条）**没有经验字段**。因此本项目严格来说是"**以招聘市场数据驱动的岗位画像与匹配系统**"，"校招"体现在：① 上述 6% 的真实应届岗位；② 推荐算法针对"无经验/应届"画像的适配设计；③ P1 计划接入的国聘网与教育部平台公开接口（真正的校招数据源）。项目书与答辩中**不宜声称数据集本身是校招数据**。

同时，招聘数据本身具有很高分析价值：技能需求分布、薪资地域差异、岗位类型趋势等，可作为求职决策的依据。

### 1.2 项目目标

构建一个**校招信息聚合与智能推荐平台**，完成从数据采集到智能推荐的完整闭环：

| 目标 | 具体指标 |
|---|---|
| 多源信息采集与清洗 | 采集 ≥ 2 个数据源的岗位数据，形成清洗流水线，输出结构化岗位表 |
| 用户画像构建 | 支持技能、城市、薪资三个维度的画像录入与标签化 |
| 岗位-用户智能匹配推荐 | 实现 2 种推荐算法，输出带可解释性理由的推荐结果 |
| 投递状态追踪看板 | 支持投递记录全流程状态管理（待投递/已投递/笔试/面试/Offer/已拒） |
| 招聘数据可视化 | ≥ 5 类图表：薪资分布、城市分布、技能词云、岗位类型、薪资-经验趋势 |

### 1.3 项目定位与边界

**本项目是课程设计**，定位为"**技术完整、逻辑自洽、可演示、可讲清**"，而非生产级商业系统。因此明确以下边界：

- ✅ **做**：完整的架构设计、可运行的代码、真实的数据处理流程、可量化的算法对比
- ❌ **不做**：高并发、分布式部署、多租户、商业级爬虫对抗、7×24 运维
- ⚠️ **取舍原则**：当"技术炫技"与"按期交付"冲突时，**一律选择按期交付**

### 2.1 用户角色

| 角色 | 说明 | 核心诉求 |

| **求职者（学生）** | 主要用户 | 录入个人画像 → 获得匹配岗位推荐 → 追踪投递进度 |

### 2.4 数据源约束（来自实测）

本项目使用**两个数据集互补**，均已实际下载验证：数据集 A（24,185 条 × 34 列，主力）、数据集 B（10,114 条 × 11 列，补充）。合并后规模 **34,299 条**。

**两个数据集的互补关系**：

| 维度 | 数据集 A（主力） | 数据集 B（补充） |
|---|---|---|
| 条数 | 24,185 | 10,114 |
| 协议 | ⚠️ README 声明 MIT，但仓库内无 LICENSE 文件 | ⚠️ 无 LICENSE |
| **技能标签** | ⚠️ **自带 18 个技能哑变量列**，但全量口径下**仅 29.9% 的行命中至少 1 项** | ❌ 需从 JD 文本抽取 |
| 结构化字段 | 薪资 + 城市 + **学历 + 经验 + 行业 + 公司规模** | 薪资 + 城市 |
| JD 文本 | 有，但 **2,085 条（8.6%）的 `description` 是空 `[]`**；有正文的均值 456 字、中位 410 字、最长 9,754 字 | 有，10,114 条中仅 5 条为空；中位 286 字、最长 5,687 字 |
| **校招标识** | ⚠️ **仅 `experience == "应届生"` 的 1,444 条（占 6.0%）**，且数据集 A 本身是社招 + 校招的混合数据 | ❌ 无 |

> **双数据集策略的价值**：数据集 A 的技能标签是**现成的 0/1 哑变量**，省去抽取工作且可直接用于推荐；但它只覆盖数据类技能（python/sql/java/spark 等）。数据集 B 的 JD 文本更丰富，可抽取 FastAPI、Vue、Docker 等开发类技能。**两者合并既保证数据量，又保证技能覆盖度。**

#### 数据集 A 实测优势

| 字段 | 缺失率 | 说明 |
|---|---|---|
| `salary_min` / `salary_max` / `salary_avg` | **0%** | **结构化数值，无需解析** |
| `description` | **0%** | JD 正文 |
| `education` / `experience` | 0% | 学历、经验要求（枚举值） |
| `company` / `city` / `industry` | 0% | 公司、城市、行业 |
| **18 个技能哑变量列** | 0% | `python`/`sql`/`excel`/`tableau`/`power_bi`/`sas`/`spss`/`r`/`java`/`spark`/`hadoop`/`机器学习`/`深度学习`/`统计`/`数据挖掘`/`可视化`/`ppt`/`mysql`，值为 0/1。**注意：全量口径下仅 29.9% 的行至少命中 1 项** |

> **关键发现**：薪资字段**自带结构化数值**且**零缺失**。这消除了原计划中"薪资字符串解析"模块，节省约 8 小时工期。

#### 数据集 B 实测优势

| 字段 | 缺失率 | 说明 |
|---|---|---|
| **`minsalary` / `maxsalary` / `meansalary`** | **0%** | **结构化，且 100% 数学自洽**（`meansalary` 严格等于 min/max 中值，`max < min` 的行数 = 0） |
| `city` / `city_idx` | 0% | 城市名 + 编码 |
| `description` | **8.6%**（2,085 条取值为 `[]`，即无正文） | JD 正文，均值 **456** 字 / 中位 **410** 字 / P90 759 字 / 最长 **9,754** 字；另有 874 条（4.0%）短于 50 字 |
| `jobname` | 0.01% | 岗位名称 |

#### ⚠️ 已知缺陷（清洗模块必须处理）

**来自数据集 A**：

| 缺陷 | 实测证据 | 处理方案 |
|---|---|---|
| **文件带 UTF-8 BOM** | 读取时首列名异常 | Python 读取用 `encoding='utf-8-sig'` |
| **list 字符串格式** | `tags`/`industry`/`company_type`/`company_size` 等列形如 `"['互联网/电子商务']"`；**`description` 更是 100% 为 list 字面量**，形如 `"['1.\xa0\xa0 以用户增长为导向…', '2.…']"` | 用 `ast.literal_eval()` 解析后 `"".join()` 拼成正文；**不能只 strip 方括号**——正文内含中文逗号、单引号与 `\xa0`（不间断空格） |
| **日期缺年份** | `publish_date` **只有 `MM-DD`、不含年份**，取值 `05-12` ~ `07-09`，共 **25 个唯一值** | **不可用于跨年或长期趋势分析**，仅作展示字段；若要用建议补一个「数据快照年份」元数据字段 |

**来自数据集 B**：

| 缺陷 | 实测证据 | 处理方案 |
|---|---|---|
| **标签分类不可信** | 生物研发岗被标为"数据分析"；正文提及大模型的 **1,293 条**中 **25.1%（324 条）被标为其他类别** | 不使用 `label` 作为推荐依据，改用技能词典重新归类 |
| **JD 混入法务样板文** | 外企 JD 尾部含 1000+ 字隐私政策、胜任力清单。实测**仅 53 条（0.5%）**含此类标记；在这些 JD 中样板文占全文比例中位约 46% | 正则剥离样板文段落（**污染面比原估计窄得多，优先级可下调**） |
| **短文本脏数据** | **464 条（4.6%）**短于 50 字符，最短仅 1 字符 | 过滤 `len(description) < 50` |
| **城市分布偏斜** | 数据集 B：北京占 **32.4%**，"其他"兜底桶占 **18.2%**。**数据集 A 恰好相反：北京只占 3.1%**（广州 16.4%、深圳 15.6%、上海 14.0%、其他 15.2%）。两源合并后"其他"桶合计约 5,500 条 | 可视化时单独标注"其他"，不参与城市排名；**按源分别出图**，避免 A 的城市分布被 B 覆盖 |
| **公司字段缺失** | 8.99% 为空（多为猎头/匿名岗） | 显示为"未知公司" |
| **技能词覆盖率** | 数据集 B 口径：至少命中 1 个技能词的 JD 占 **75.2%**；**数据集 A 口径：现成的 18 个技能列只覆盖 29.9%（全量）/ 64.3%（纯数据岗子集）** | 技能词典需覆盖常见 IT 技能词；**两个口径在报告中必须分开标注，不可混用** |
| **非目标岗位混入** | 数据集 B 的 `label` 分布：数据分析 26.2%、经济金融 20.7%、生物统计 19.2%、算法岗 18.8%、大模型相关 15.1%。**经济金融 + 生物统计 = 4,034 条（39.9%），与"技能匹配"主线弱相关**（实测首行就是生物实验岗的英文 JD） | 按 `label` + 岗位名关键词过滤，或至少在图表的样本说明中披露口径 |

#### ⚠️ 跨源合并与数据集定位的实测约束

上面两张表是**按源分别统计**的结果。两个源合并成 34,299 条时，还有三条实测约束必须在设计里体现：

**① 两源几乎没有重叠岗位，且不能用 `job_title` 做跨源对齐。**

| 对齐方式 | 实测结果 |
|---|---|
| 按 `岗位名 + 公司` 求交集 | **只有 3 条重复**（合并去重后 **34,296 条**，不是 34,299） |
| 按 `job_title == jobname` 内连接 | **炸出 321,544 行**——字段名相同但语义不对应，会产生笛卡尔式膨胀 |

> **结论**：合并只能取**并集**，且 **`jobs` 表必须新增 `source` 字段**（取值 `dataset_a` / `dataset_b` / `boss_zhipin` / `offline`），否则后续无法按源分析、无法解释城市与技能的分布偏斜，也无法在演示时回答"这个数字来自哪个数据集"。

**② 数据集 B 的 `salary` 列是元组字符串，清洗时不要解析它。**

实测形如 `'(25000.0, 50000.0)'`（字符串，不是数值）。而 `minsalary`/`maxsalary`/`meansalary` 三列已是数值且 **100% 数学自洽**——`meansalary` 严格等于 min/max 中值，`max < min` 的行数为 0（实测 10,114/10,114 行全部通过）。数据集 A 的 `salary_min`/`salary_max`/`salary_avg` 同样 **100% 自洽且零缺失**（24,185/24,185 行通过，`salary_avg` 取值 1,000 ~ 75,000 元）。

**③ 技能命中率决定演示集的选择。**

| 数据集 | 条数 | 至少命中 1 项技能 |
|---|---:|---:|
| `cleaned_all.csv`（A 全量） | 24,185 | **29.9%** |
| `cleaned_data_jobs.csv`（A 纯数据岗） | 2,915 | **64.3%** |
| `job_posting_data_B.xlsx`（B） | 10,114 | 75.2%（词典口径） |

> **建议**：把 `cleaned_data_jobs.csv`（2,915 条纯数据岗，技能覆盖率 64.3%）作为**推荐功能的主演示集**，`cleaned_all.csv` 只承担统计图表的规模底座。"技能 → 岗位"是推荐主线，演示集技能命中率越高，推荐理由越充实、越不像随机结果——**工作量不增加，演示效果明显更好**。

### 3.3 关键调研发现：BOSS直聘反爬机制

这是本次调研**最有价值的技术发现**，直接决定爬虫模块的可行性。

#### 反爬机制分析

BOSS直聘列表页的薪资数字**不是普通文本**，而是用**动态生成的 woff 字体**渲染的——直接抓取 DOM 的 `textContent` 会得到私用区码点（U+E000–U+F8FF）乱码。

| 破解路线 | 做法 | 可行性 |
|---|---|---|
| ❌ 字体逆向 | 下载 woff 建立码点→数字映射表 | **不可行**：字体**每次访问动态生成**，映射表无法复用 |
| ❌ OCR 识别 | 截图后文字识别 | 慢、易错、演示可靠性差 |
| ✅ **调用内部 API** | 请求 `/wapi/zpgeek/search/joblist.json`，其 **`salaryDesc` 字段是明文**（如 `30-60K·15薪`） | **推荐方案** |
| ✅ 详情页解析 | 列表页加密，但**岗位详情页薪资为明文** | 降级方案，约 300 页/20 分钟 |

#### 原理（可用于答辩）

> **字体加密只是前端渲染层的对抗手段。** 前端自身需要展示薪资，因此数据在接口层必须是明文——字体加密只防住了"从 DOM 抠文字"的采集方式，没有防住"直接调接口"的方式。

#### 技术路线

```
Chrome CDP 连接已登录浏览器实例
    ↓
注入 JS 调用内部 API（或被动监听页面自身发出的搜索请求，降低风控识别）
    ↓
提取 salaryDesc 明文字段 → 落盘去重（按 job_id）
```

**实现要点**：
- 必须在**已登录的真实浏览器上下文**中调用（`/wapi/` 接口有 cookie 校验）
- 使用**持久化独立 profile**，不触碰主浏览器登录态
- 分页不可靠（`page=2` 常返回空），改用滚动加载 + 筛选条件变化
- 需处理 `__zp_stoken__` 签名参数，风控码需自动刷新或降级

#### 合规约束

| 约束 | 措施 |
|---|---|
| robots.txt | 采集前检查并遵守 |
| 请求频率 | 随机延迟 + 人类化滚动，控制 QPS |
| 个人信息 | **不采集**招聘者姓名、联系方式等个人身份信息 |
| 用途限定 | 仅用于课程设计演示，不传播、不商用 |
| 降级机制 | 触发安全验证时**立即停止**，不尝试绕过验证码 |

> **本项目实现策略**：完整实现爬虫代码（体现技术能力），但演示时使用**离线数据包**。爬虫仅在小规模下验证可行性，这是对"演示稳定性"与"技术展示"的平衡。

### 3.4 必须避开的坑（避坑清单）

| # | 坑 | 具体表现 | 规避措施 |
|---|---|---|---|
| 1 | **高 star ≠ 适合** | `full-stack-fastapi-template` 44.4k star，但官方 Discussion 标题即为 ["Not Beginner Friendly Project"](https://github.com/fastapi/full-stack-fastapi-template/discussions/1115)：Docker 配置无文档、**前端是 React 不是 Vue**、默认 **PostgreSQL 不是 MySQL**、多层 compose 文件 | **按技术栈匹配度选型**，不按 star 数 |
| 2 | **爬虫项目按 star 选必踩雷** | 停更 7-9 年的爬虫项目仍有高 star，代码 100% 失效 | **以最后更新时间为第一筛选条件** |
| 3 | **协同过滤没有数据支撑** | 强行实现会得到"跑得通但推不准"的空壳，答辩无法解释 | 选择**基于内容**的推荐路线 |
| 4 | **过度设计** | 引入 Redis + Celery + Docker + Scrapy 分布式，调试成本压垮工期 | **YAGNI 原则**，只做交付必需 |
| 5 | **数据集标签盲信** | 该数据集 `label` 一致性最低仅 43.8%（算法岗），直接使用会误导 | **不直接使用 `label`**，基于技能词典重新归类 |
| 6 | **JD 样板文污染** | 企业法务文本（隐私政策、胜任力清单）在含此类内容的 JD 中占全文约 46%，但此类 JD 仅 53 条（0.5%），**污染面很窄** | 清洗阶段剥离样板文；优先级下调 |
| 7 | **毛玻璃背景不铺** | 纯色背景上毛玻璃 = 灰方块，完全无效果 | 必须先铺固定渐变背景层（见 8.2 节） |
| 8 | **表格逐行加模糊** | 50 行表格 = 50 个模糊层 = 必然卡顿 | 只在容器层加一次 `backdrop-filter` |

|---|---|---|
| 1 | **数据质量校验机制** | 多数项目直接使用数据集；本项目在清洗阶段**量化验证**薪资自洽率（100%）、标签一致性（最低 43.8%）、技能覆盖率（数据集 B 口径 75.2%；数据集 A 现成的 18 个技能列全量仅 29.9%），并据此调整算法输入 |
| 2 | **不盲信数据集标签** | 发现 `label` 噪音后，改用**技能词典驱动的重新归类**，并把这个发现作为报告的数据分析章节 |
| 3 | **推荐可解释性** | 输出不仅给分数，还给**命中项明细**（哪些技能命中、城市是否匹配、薪资落在哪个区间） |
| 4 | **双算法对比实验** | 用人工标注的 100 条测试集，计算 Precision@10 / 命中率，**量化对比**加权规则与 TF-IDF |
| 5 | **采集双通道架构** | `DataSource` 抽象接口同时支持真实爬虫与离线数据包，**演示稳定性与技术支持性分离** |
| 6 | **毛玻璃数据看板** | 采用 Glassmorphism 设计，深色主题 + ECharts 透明化，视觉表现优于同类项目的默认后台样式 |

**关键接口定义**：

```python
# services/collector/base.py
class DataSource(ABC):
    """采集器抽象基类 —— 所有数据源统一实现此接口"""

    @abstractmethod
    def fetch(self, **kwargs) -> list[dict]:
        """采集原始数据，返回标准化字典列表"""
        ...

    @property
    @abstractmethod
    def source_name(self) -> str:
        """数据源标识，用于采集日志"""
        ...
```

> **设计说明**：这个抽象接口是"多源采集"要求的**架构落地**。新增数据源只需实现 `fetch()`，无需修改调用方代码——这是**适配器模式 + 依赖倒置原则**的体现，答辩时可重点讲解。

### 4.5 数据流

**流程一：数据采集入库（离线脚本，手动触发）**

```
运行 scripts/import_dataset.py
    ↓
选择数据源适配器（offline_a / offline_b / boss）
    ↓
fetch() 采集 → List[RawJob]
    ↓
cleaner 清洗：
    ├─ 去重（按 jobname + company + description 哈希）
    ├─ 过滤（description < 50 字符）
    ├─ 剥离样板文（正则匹配隐私政策/胜任力清单段落）
    └─ 城市标准化（"其他" 单独标记）
    ↓
jd_parser 抽取技能标签 → job.skills
    ↓
批量写入 jobs 表（按 source + external_id 幂等）
    ↓
写入 collect_logs 表（记录条数、耗时、状态）
```

**流程二：用户推荐（在线接口）**

```
用户请求 GET /api/v1/recommend?algorithm=weighted
    ↓
加载用户画像（skills, expect_city, expect_salary）
    ↓
加载候选岗位集（默认全量，可加筛选条件缩小范围）
    ↓
推荐引擎：
    ├─ algorithm=weighted → 加权规则打分
    └─ algorithm=tfidf    → TF-IDF 向量化 + 余弦相似度
    ↓
排序 → 取 Top N
    ↓
生成可解释理由（命中技能明细、城市/薪资匹配情况）
    ↓
返回 List[RecommendResult]
```

**流程三：投递追踪**

```
推荐列表点击"加入投递" → POST /api/v1/applications
    ↓
创建投递记录（状态 = 待投递）
    ↓
用户在看板更新状态（已投递 → 笔试 → 面试 → Offer/已拒）
    ↓
PATCH /api/v1/applications/{id}
    ↓
看板统计实时更新
```

**关系说明**：

| 关系 | 类型 | 说明 |
|---|---|---|
| `users` → `user_profiles` | 1:1 | 一个用户一份画像 |
| `users` → `applications` | 1:N | 一个用户多条投递记录 |
| `jobs` → `applications` | 1:N | 一个岗位可被多次投递（不同用户） |
| `jobs` ↔ `skills` | N:N（逻辑） | 通过 `jobs.skills` JSON 字段关联，**不建中间表**（见下方设计说明） |

> **设计说明（重要，答辩可能被问）**：
> 岗位与技能在**规范化的数据库设计**中应使用中间表 `job_skills` 实现 N:N 关系。本项目**有意不使用中间表**，理由：
> 1. **数据量小**：1 万条岗位 × 平均 5 个技能 = 5 万行中间表，收益极低
> 2. **查询模式简单**：技能仅用于推荐打分时在**应用层**做集合运算，**从不需要"按技能反查岗位"的 SQL 查询**
> 3. **MySQL 8.0 支持 JSON 类型**：`JSON_CONTAINS()` 函数足以支撑必要的查询
>
> 这是一个**有意识的取舍**，不是设计疏漏。如果面试/答辩被质疑，可以回答："在需要按技能维度做复杂关联查询的场景下，我会引入中间表；但本场景的查询模式是应用层集合运算，中间表只会增加 join 开销。"

## 6. API 接口契约

> **本节是前后端并行开发的依据。接口一旦冻结，前端即可按此开发，无需等待后端完成。**

### 6.1 通用约定

**Base URL**：`http://localhost:8000/api/v1`

**鉴权方式**：除注册/登录外，所有接口需在请求头携带 Token

```
Authorization: Bearer <access_token>
```

**统一响应格式**：

```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | `0` 表示成功，非 0 表示业务错误 |
| `message` | string | 提示信息（中文） |
| `data` | any | 业务数据，可以是对象、数组或 null |

**分页响应格式**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 120,
    "page": 1,
    "page_size": 20
  }
}
```

**分页请求参数**（通用）：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 页码，从 1 开始 |
| `page_size` | int | 20 | 每页条数，最大 100 |

**错误码定义**：

| code | HTTP | 含义 |
|---|---|---|
| `0` | 200 | 成功 |
| `1001` | 400 | 参数校验失败 |
| `1002` | 401 | 未登录或 Token 失效 |
| `1003` | 403 | 无权限 |
| `1004` | 404 | 资源不存在 |
| `1005` | 409 | 资源冲突（如用户名已存在、重复投递） |
| `2001` | 500 | 服务器内部错误 |
| `2002` | 503 | 数据源不可用（如爬虫失败） |

### 7.2 前置处理：JD 解析与技能抽取

推荐算法的输入质量取决于技能抽取的准确性。本模块分三步：

#### 步骤 1：样板文剥离（清洗）

**问题**：实测发现**少数**外企/大厂 JD 尾部含 1000+ 字符的企业法务文本（隐私政策、胜任力清单）；此类 JD 仅 **53 条（占数据集 B 的 0.5%）**，在这些 JD 中样板文占全文比例中位约 **46%**。绝对数量虽少，但单条 JD 的污染很重，仍值得剥离。（**注**：数据集 B 真正更值得警惕的污染是**非目标岗位**——见 2.4 节跨源实测约束。）

**方案**：正则匹配 + 段落位置启发式

```python
# services/cleaner.py
import re

# 样板文特征模式
BOILERPLATE_PATTERNS = [
    r'隐私政策.*?(?=\n\n|$)',           # 隐私政策段落
    r'个人信息保护.*?(?=\n\n|$)',        # 个人信息条款
    r'胜任力.*?(?=\n\n|$)',             # 胜任力清单
    r'Global Competencies.*?(?=\n\n|$)', # 英文胜任力
    r'求职者须知.*?(?=\n\n|$)',          # 求职须知
]

def strip_boilerplate(text: str) -> str:
    """剥离 JD 中的企业法务样板文"""
    if not text:
        return ""
    # 1. 按模式删除样板文段落
    for pattern in BOILERPLATE_PATTERNS:
        text = re.sub(pattern, '', text, flags=re.DOTALL | re.IGNORECASE)

    # 2. 中英文重复内容去重（法务文本常中英各一遍）
    paragraphs = [p.strip() for p in text.split('\n') if p.strip()]
    seen = set()
    deduped = []
    for p in paragraphs:
        key = p[:50]  # 用前 50 字符作为指纹
        if key not in seen:
            seen.add(key)
            deduped.append(p)

    return '\n'.join(deduped)
```

#### 步骤 2：jieba 分词 + 技能词典匹配

**关键设计**：**不使用**数据集自带的 `label` 字段，而是基于技能词典重新归类。

> **理由（重要）**：实测发现 `label` 分类噪音很大——生物研发岗被标为"数据分析"；正文提及大模型的 **1,293 条**中 **25.1%（324 条）被标为其他类别**。算法岗标签与正文的一致性只有 **43.3%**（项目书原写的 43.8% 用的是另一套判定规则，数量级一致，保留亦可）。直接使用 `label` 会误导推荐结果。

```python
# services/jd_parser.py
import jieba
import re

class JDParser:
    def __init__(self, skill_dict_path: str):
        # 加载技能词典到 jieba（确保 "机器学习" 不被切成 "机器"+"学习"）
        jieba.load_userdict(skill_dict_path)
        self.skill_set = self._load_skills(skill_dict_path)
        # 额外处理：英文技能词的大小写与符号
        self.alias_map = self._build_alias_map()

    def extract_skills(self, description: str) -> list[str]:
        """从 JD 文本抽取技能标签"""
        if not description:
            return []

        found = set()

        # 策略 1：直接字符串匹配（处理 Python、C++ 等英文技能）
        text_lower = description.lower()
        for skill, aliases in self.alias_map.items():
            for alias in aliases:
                # 用词边界避免 "go" 匹配到 "google"
                if self._match_with_boundary(text_lower, alias):
                    found.add(skill)
                    break

        # 策略 2：jieba 分词匹配（处理中文技能如 "机器学习"）
        words = set(jieba.cut(description))
        for word in words:
            if word in self.skill_set:
                found.add(word)

        return sorted(found)

    def _match_with_boundary(self, text: str, keyword: str) -> bool:
        """带边界的匹配，避免子串误匹配"""
        # 纯 ASCII 关键词用 \b 边界
        if keyword.isascii():
            pattern = r'\b' + re.escape(keyword) + r'\b'
        else:
            pattern = re.escape(keyword)
        return bool(re.search(pattern, text, re.IGNORECASE))

    def classify_job_type(self, skills: list[str]) -> str:
        """基于技能集合归类岗位类型（替代数据集的 label）"""
        # 按技能命中数投票
        scores = {}
        for job_type, type_skills in JOB_TYPE_SKILL_MAP.items():
            hit = len(set(skills) & set(type_skills))
            if hit > 0:
                scores[job_type] = hit
        if not scores:
            return "其他"
        return max(scores, key=scores.get)


# 岗位类型 → 关键技能映射
JOB_TYPE_SKILL_MAP = {
    "后端开发":   ["Python", "Java", "Go", "FastAPI", "Django", "Spring Boot", "MySQL", "Redis"],
    "前端开发":   ["JavaScript", "Vue", "React", "HTML", "CSS"],
    "数据分析":   ["SQL", "数据分析", "统计学", "Excel", "Tableau"],
    "算法工程":   ["机器学习", "深度学习", "PyTorch", "TensorFlow", "大模型"],
    "测试工程":   ["自动化测试", "Selenium", "pytest", "性能测试"],
}
```

### 7.3 算法 A：加权规则匹配

#### 设计思想

将"人岗匹配"分解为**三个独立维度**，各自打分后加权求和。优势是**每一步都可解释**。

#### 打分规则

| 维度 | 权重 | 打分方式 |
|---|---|---|
| **技能匹配** | 50% | 命中技能数 / 岗位要求技能数 |
| **城市匹配** | 30% | 完全匹配 100；未填期望城市则给基准分 50（避免惩罚） |
| **薪资匹配** | 20% | 按区间重叠比例计算 |

#### 复杂度分析

| 维度 | 复杂度 | 说明 |
|---|---|---|
| 技能匹配 | O(n·m) | n=用户技能数（约 5-10），m=岗位技能数（约 3-8），实际运算量极小 |
| 城市匹配 | O(1) | 字符串比较 |
| 薪资匹配 | O(1) | 区间运算 |
| **整体** | **O(N)** | N=候选岗位数。1 万条岗位的线性扫描在 Python 中约 50-150ms，**满足 < 500ms 的性能要求** |

#### 核心实现

```python
# services/recommender.py
from decimal import Decimal

class WeightedRecommender:
    """算法 A：加权规则匹配"""

    WEIGHTS = {
        "skill": 0.5,
        "city": 0.3,
        "salary": 0.2,
    }

    def score(self, profile: dict, job: dict) -> dict:
        """计算单个岗位的匹配分，返回分数与理由明细"""
        skill_score, skill_detail = self._score_skill(profile, job)
        city_score, city_detail = self._score_city(profile, job)
        salary_score, salary_detail = self._score_salary(profile, job)

        total = (
            skill_score * self.WEIGHTS["skill"]
            + city_score * self.WEIGHTS["city"]
            + salary_score * self.WEIGHTS["salary"]
        )

        return {
            "match_score": round(total, 2),
            "reasons": [
                {"type": "skill",  "detail": skill_detail,  "score": round(skill_score, 2),  "weight": self.WEIGHTS["skill"]},
                {"type": "city",   "detail": city_detail,   "score": round(city_score, 2),   "weight": self.WEIGHTS["city"]},
                {"type": "salary", "detail": salary_detail, "score": round(salary_score, 2), "weight": self.WEIGHTS["salary"]},
            ],
        }

    # ---------- 维度 1：技能（权重 0.5） ----------
    def _score_skill(self, profile: dict, job: dict) -> tuple[float, str]:
        user_skills = set(profile.get("skills") or [])
        job_skills = set(job.get("skills") or [])

        if not job_skills:
            return 60.0, "该岗位未提取到技能要求，按基准分计算"
        if not user_skills:
            return 0.0, "尚未填写技能标签"

        hit = user_skills & job_skills
        score = len(hit) / len(job_skills) * 100

        if hit:
            detail = f"命中 {len(hit)}/{len(job_skills)} 项技能：{'、'.join(sorted(hit))}"
            if len(hit) < len(job_skills):
                miss = job_skills - user_skills
                detail += f"；未命中：{'、'.join(sorted(miss))}"
        else:
            detail = f"未命中任何要求技能（岗位要求：{'、'.join(sorted(job_skills))}）"

        return score, detail

    # ---------- 维度 2：城市（权重 0.3） ----------
    def _score_city(self, profile: dict, job: dict) -> tuple[float, str]:
        expect_city = profile.get("expect_city")
        job_city = job.get("city")

        # 用户未填期望城市 → 给中性分，避免误惩罚
        if not expect_city:
            return 50.0, "未设置期望城市，按中性分计算"

        if expect_city == job_city:
            return 100.0, f"期望城市「{expect_city}」与岗位城市一致"

        return 0.0, f"期望城市「{expect_city}」，岗位城市「{job_city}」，不匹配"

    # ---------- 维度 3：薪资（权重 0.2） ----------
    def _score_salary(self, profile: dict, job: dict) -> tuple[float, str]:
        """按薪资区间重叠比例打分 —— 部分重叠给部分分，不是非黑即白"""
        exp_min = profile.get("expect_salary_min")
        exp_max = profile.get("expect_salary_max")
        job_min = job.get("salary_min")
        job_max = job.get("salary_max")

        if exp_min is None or exp_max is None:
            return 50.0, "未设置期望薪资，按中性分计算"
        if job_min is None or job_max is None:
            return 50.0, "该岗位薪资信息缺失，按中性分计算"

        # 计算区间重叠
        overlap_min = max(exp_min, job_min)
        overlap_max = min(exp_max, job_max)

        if overlap_max <= overlap_min:
            # 无重叠：判断是偏高还是偏低
            if job_max < exp_min:
                detail = f"岗位薪资 {self._fmt(job_min)}-{self._fmt(job_max)} 低于期望"
            else:
                detail = f"岗位薪资 {self._fmt(job_min)}-{self._fmt(job_max)} 高于期望"
            return 0.0, detail

        overlap_ratio = (overlap_max - overlap_min) / (exp_max - exp_min)
        score = overlap_ratio * 100

        if overlap_ratio >= 0.99:
            detail = f"薪资 {self._fmt(job_min)}-{self._fmt(job_max)} 完全落在期望区间内"
        else:
            detail = f"薪资区间部分重叠（重叠比例 {overlap_ratio*100:.0f}%）"

        return score, detail

    @staticmethod
    def _fmt(value: int) -> str:
        """格式化为 K 显示"""
        return f"{value/1000:.0f}K" if value >= 1000 else str(value)
```

### 7.4 算法 B：TF-IDF 相似度

#### 设计思想

将用户画像"文档化"（把技能和工作期望拼成一段文本），与 JD 文本分别做 TF-IDF 向量化，计算**余弦相似度**。优势是能捕捉**语义上的词汇重要性**——罕见技能词权重更高。

#### 核心实现

```python
# services/recommender.py
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np


class TfidfRecommender:
    """算法 B：TF-IDF 文本相似度"""

    def __init__(self, corpus: list[str]):
        """
        corpus: 全部岗位的 JD 文本列表
        注意：IDF 必须在整个语料库上计算，而不是逐条计算
        """
        self.vectorizer = TfidfVectorizer(
            tokenizer=self._tokenize,       # 用 jieba 分词
            lowercase=True,
            max_features=5000,              # 限制特征维度，控制内存
            min_df=2,                       # 忽略仅出现 1 次的词（降噪）
        )
        self.job_matrix = self.vectorizer.fit_transform(corpus)

    def _tokenize(self, text: str) -> list[str]:
        """jieba 分词 + 去停用词"""
        import jieba
        words = jieba.cut(text)
        return [w.strip() for w in words if w.strip() and w not in STOPWORDS]

    def build_user_document(self, profile: dict) -> str:
        """把用户画像转成一段'查询文档'"""
        parts = []
        if profile.get("skills"):
            # 技能权重放大：重复 3 次，让技能词在 TF 上占优
            parts.extend(profile["skills"] * 3)
        if profile.get("expect_city"):
            parts.append(profile["expect_city"])
        if profile.get("expect_job_type"):
            parts.append(profile["expect_job_type"])
        return " ".join(parts)

    def recommend(self, profile: dict, top_n: int = 20) -> list[dict]:
        """返回带相似度分数的推荐结果"""
        user_doc = self.build_user_document(profile)
        if not user_doc.strip():
            return []

        user_vec = self.vectorizer.transform([user_doc])
        # 余弦相似度：值域 [0, 1]
        sims = cosine_similarity(user_vec, self.job_matrix).flatten()

        top_indices = np.argsort(sims)[::-1][:top_n]
        return [
            {"job_index": int(i), "match_score": round(float(sims[i]) * 100, 2)}
            for i in top_indices
        ]
```

#### 关键设计点（答辩可讲）

| 设计点 | 说明 |
|---|---|
| **技能词重复 3 次** | TF-IDF 中 TF（词频）影响权重。技能是用户最关心的信号，通过重复提升其 TF 值，让技能词在相似度计算中占更高比重 |
| **`max_features=5000`** | 限制特征维度。1 万条 JD 的全量词表可能有 10 万+ 维度，稀疏矩阵虽不占内存但计算慢；5000 维覆盖了绝大多数有效信息 |
| **`min_df=2`** | 过滤只出现一次的词（多为噪声、错别字、公司专有名词），提升向量质量 |
| **IDF 在全语料库上计算** | TF-IDF 的 IDF 项衡量"词的稀有程度"，**必须在全量语料上统计**才有意义。逐条计算是常见错误 |
| **余弦相似度而非欧氏距离** | 文本长度差异大（实测数据集 A 的 JD 正文从 5 字到 9,754 字），余弦相似度对长度不敏感，欧氏距离会被长文本主导 |

#### 与算法 A 的对比

| 维度 | 算法 A（加权规则） | 算法 B（TF-IDF） |
|---|---|---|
| **原理** | 显式特征加权求和 | 文本向量空间余弦相似度 |
| **优势** | 完全可解释；支持硬性约束（城市） | 能捕捉词汇重要性；无需人工设权重 |
| **劣势** | 权重需人工设定；无法处理同义词 | 结果难解释；长文本可能主导 |
| **城市约束** | ✅ 强约束（不匹配直接 0 分） | ⚠️ 弱约束（城市词权重低，可能被淹没） |
| **可解释性** | ⭐⭐⭐⭐⭐ 每项都有明细 | ⭐⭐ 只有一个分数 |
| **计算复杂度** | O(N)，1 万条约 100ms | O(N·d)，d=5000 维，约 200ms |
| **适合场景** | 用户有明确偏好（城市/薪资硬约束） | 用户只给了技能，想探索更多可能 |

#### 结果分析方向（报告写作框架）

1. **总体表现**：哪个算法 Precision@10 更高？
2. **场景差异**：城市约束强的用户（如 U1 杭州），算法 A 是否明显更优？（因为算法 A 有硬约束）
3. **失败案例分析**：算法 B 是否出现"推荐了技能相似但城市完全不符"的岗位？这印证了什么？
4. **结论**：两种算法**不是替代关系而是互补关系**——提出"**算法 A 做粗排（含硬约束）+ 算法 B 做精排（语义相似）**"的混合方案作为改进方向

> **这个"混合推荐"的改进方向是答辩的加分点**：它表明你理解两种算法的适用边界，而不是简单地说"A 比 B 好"。

#### 8.2.7 性能红线

| 规则 | 原因 |
|---|---|

| 全局 `backdrop-filter` 出现次数 **≤ 10 处** | 验收时全局搜索确认 |

### 13.2 核心答辩要点（你的部分）

#### 要点 1：为什么爬虫只做了一个源？

> "课程要求是多源采集，我在**架构上**用适配器模式做了多源支持——`DataSource` 抽象接口，目前已实现 4 个适配器。但**真实网络采集我只实现了 BOSS直聘 1 个源**，原因是：招聘网站的反爬成本很高，而我的交付周期只有 42 天。我选择把时间投入在**数据处理和推荐算法**这两个课程重点上，而不是对抗反爬。这是我的**工程取舍**。"

#### 要点 2：数据质量分析（**最亮眼的部分**）

> "我对数据集做了**量化质量校验**，发现三个问题：① 数据集自带的岗位分类标签，与 JD 正文的一致性最低只有 **43.3%**（算法岗，按自有判定规则实测）——比如一个生物研发岗被标成了'数据分析'。所以**我没有直接使用这个标签**，而是基于清华 THUOCL 词库重新做了岗位归类。② 少数外企 JD 尾部混入了企业法务样板文，实测只有 53 条（占数据集 B 的 0.5%），但在这些 JD 里占全文约 46%，会污染技能抽取，所以我写了剥离逻辑。③ 薪资字段我验证了数学自洽性，**100% 自洽、0 条异常**，所以这部分可以直接使用。"

#### 要点 3：为什么不用协同过滤？

> "协同过滤需要**大量用户行为数据**，而课程设计场景下没有真实用户。强行实现会得到一个'跑得通但推不准'的空壳，而且**无法解释推荐理由**。所以我选择了**基于内容的推荐**——用技能、城市、薪资三个显式特征做匹配，每个推荐结果都能给出具体理由。"

#### 要点 4：算法对比的结论

> "加权规则在**有明确城市偏好**的用户上表现更好（因为城市是硬约束）；TF-IDF 在**只给了技能**的用户上更好（能捕捉语义相似）。所以我的结论是：**两者不是替代关系，而是互补关系**——改进方向是'加权规则做粗排 + TF-IDF 做精排'的混合方案。"

### 13.3 可能被问到的技术问题

| 老师可能问 | 回答思路 |
|---|---|
| **为什么技能字段用 JSON 不建中间表？** | 规范设计应建中间表；但本场景技能只在应用层做集合运算，从不做"按技能反查岗位"的 SQL 查询，且 MySQL 8.0 的 JSON 类型足够支撑。**这是有意识的取舍，不是疏漏**。（见 5.1 节设计说明） |
| **密码怎么存的？** | bcrypt 哈希，不可逆。数据库里看不到明文。 |
| **SQL 注入怎么防？** | 全部使用 SQLAlchemy ORM 参数化查询，不拼接 SQL 字符串。 |
| **推荐结果为什么是这个分数？** | **现场演示**：展示"推荐理由"面板，逐项说明技能/城市/薪资各自的得分和权重。 |
| **技能抽取怎么做的？** | jieba 分词 + 清华 THUOCL 自定义词典。英文技能用词边界正则匹配（避免 `go` 误匹配 `google`），中文技能用分词结果匹配词典。 |
| **数据量多少？** | 两个数据集合并 34,299 条（去重后 **34,296 条**）。**注意：两个数据集的发布日期字段都不含年份**——数据集 A 的 `publish_date` 仅 25 个 `MM-DD` 取值（05-12 ~ 07-09），JD 正文里也查不到年份证据，因此**不能声称"涵盖 2025-2026 年"**，只能说明是同一采集窗口内的快照。 |
| **算法效果怎么评估的？** | 人工构造 10 个虚拟用户画像，每个标注 10 个合理岗位，计算 Precision@10。 |
| **前端毛玻璃怎么实现的？** | `backdrop-filter: blur()`。关键难点是**性能**——表格不能逐行加模糊，只在容器层加一次。另外必须铺背景层，否则看不出效果。 |
| **如果让你继续做，下一步做什么？** | ① 补充真实校招数据（已调研到国聘网和教育部平台的公开接口）；② 混合推荐（粗排+精排）；③ 引入简历解析，自动生成画像。 |

```
2. 进入「用户画像」，选择技能、填写城市/薪资    （20 秒）
   └─ 选择：Python、MySQL、FastAPI；城市：杭州；薪资：8K-15K
3. 进入「推荐列表」，展示推荐结果              （40 秒）
   └─ 展示匹配分、推荐理由明细
   └─ 切换到 TF-IDF 算法，对比结果差异
4. 点击「加入投递」，进入「投递看板」           （20 秒）
   └─ 演示状态流转：待投递 → 已投递 → 面试
   └─ 展示看板统计
5. 进入「数据可视化」大屏                      （40 秒）
   └─ 薪资分布、城市分布、技能词云、岗位类型
   └─ 说明毛玻璃效果的技术实现
6. 进入「后台管理」，展示采集日志与技能词典     （20 秒）
7. 展示算法对比实验图表                        （30 秒）
   └─ Precision@10 对比、失败案例分析
```

**总时长约 3 分钟**，预留 1 分钟应对提问。
